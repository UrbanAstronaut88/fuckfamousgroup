# Первый запуск fckfamous.group

## Что у нас есть

GoDaddy хранит регистрацию домена. GitHub хранит исходный код. Хостинг запускает сайт.
Покупка домена и отправка кода на GitHub сами по себе сайт не запускают.

Приложение находится в `store/`: React/Vinext, Cloudflare Worker, база D1 и файлы R2.
Это не Python-приложение и не просто статическая страница. PyCharm используется как редактор.
Один Git-репозиторий находится в корне; вложенный пустой `store/.git` сохранён в игнорируемой
папке `store/.sites-runtime/empty-nested-git-backup`.

Адреса `/#catalog`, `/#about`, `/#delivery` переключают разделы одной страницы.
Символ `#` не отправляется серверу. Он не мешает публикации; Back/Forward продолжают работать.
Админка имеет обычный путь `/dima_dinamo_admin`, API — `/api/...`.

## 1. Подготовить код

Из корня проекта включите проверку перед коммитом:

```powershell
git config core.hooksPath .githooks
cd store
npm ci
npm run security:history
npm audit --audit-level=moderate
npx tsc --noEmit
npm run lint
npm run build
node scripts/test-security.mjs
```

Не заменяйте существующий `.dev.vars`: в нём ключ проверки текущего пароля и TOTP.
Для новой установки образец — `store/.env.sample`. В этом проекте локальные секреты
читаются из `.dev.vars`, поэтому файл `.env.sample` сам по себе ничего не включает.
`store/.env.example` также оставлен для совместимости.

Состояние проверки на 06.10.2026: Next.js обновлён до 16.3.8, исправлены зависимости
source-map-js и undici. Остаётся GHSA-vfj7-8cjw-p6xm в braces 3.0.3, пришедшем через
ESLint / fast-glob. Исправления upstream пока нет. `npm audit` и соответствующий шаг
GitHub Actions остаются красными; предупреждение не подавлено. Нужны исправление upstream
либо отдельное обоснованное решение по этому риску до объявления релиза готовым.
Источник: https://github.com/advisories/GHSA-vfj7-8cjw-p6xm

## 2. Отправить в GitHub

Настроенный адрес: https://github.com/UrbanAstronaut88/fuckfamousgroup.git.
Рекомендуется private-репозиторий. Не меняйте видимость на public до проверки состава файлов.

Из корня репозитория:

```powershell
git status
git add .
node store/scripts/check-secrets.mjs --staged --history
git diff --cached --stat
git commit -m "Prepare merch site for deployment"
git push -u origin develop
```

В отправке должны быть исходники, миграции, package-lock.json и public/.
Не должны быть `.dev.vars`, реальные `.env*`, `.wrangler`, `.sites-runtime`, `.aws`, базы,
node_modules, dist и резервные копии. Проверка шаблонов не даёт абсолютной гарантии:
не записывайте новые пароли в исходники, документы, скриншоты или историю Git.

Рабочая ветка — `develop`; `main` пока содержит только начальный коммит. После прохождения проверок переносите релиз в `main` через Pull Request. Не используйте `git push origin main` для отправки текущей работы из develop.

Во вкладке GitHub **Actions** находятся результаты сборки и проверки безопасности.
Отправка кода на GitHub не переносит товары из локальной базы и фотографии из R2.

## 3. Выбрать место размещения

Текущая тестовая публикация использует управляемый Sites и отдельные D1/R2.
Её база не является автоматически базой вашего аккаунта Cloudflare.

Для самостоятельного размещения логичный вариант — Cloudflare Workers + D1 + R2.
Выбран аккаунт владельца Cloudflare. Вход Wrangler нужно выполнить на компьютере владельца.
Текущий `wrangler.jsonc` предназначен для локальной разработки: ID базы из нулей — заглушка.
Его нельзя просто отправить на production. Нужно подготовить отдельную конфигурацию
с настоящими ресурсами аккаунта и проверить результат сборки. Команды создания ресурсов
выполняются только после входа в нужный аккаунт; возможные платные условия принимает владелец.

Последовательность:

1. Войти в Cloudflare и включить двухфакторную защиту аккаунта.
2. Создать D1 и R2 для production; записать привязки `DB` и `MEDIA` в конфигурацию запуска.
3. Выбрать способ переноса каталога. Если каталог уже отредактирован локально, сначала
   сохранить резервную копию и переносить данные и загруженные изображения согласованно.
   Простая публикация создаст начальные позиции, а не перенесёт ваши изменения.
4. Для новой базы применить миграции; существующую не инициализировать повторно.
5. Настроить серверные Secrets: `ADMIN_SECRET`, `ADMIN_LOGIN`, при новом администраторе
   временный `ADMIN_INITIAL_CREDENTIAL`. Никогда не записывать их в GitHub-код.
6. Выполнить сборку и публикацию на технический адрес хостинга; только затем подключать домен.

Если хостинг собирает репозиторий, корневая директория приложения — **store**,
Node.js — **22**, установка — **npm ci**, сборка для своего Cloudflare — **npm run build:cloudflare**.
Команда публикации зависит от подготовленной конфигурации. Автодеплой пока не включён.

### Команды для своего Cloudflare

Все команды ниже выполняются в папке `store`. Сначала авторизация:

```powershell
$env:WRANGLER_WRITE_LOGS = "false"
$env:WRANGLER_LOG_PATH = ".wrangler/logs"
npx wrangler login
npx wrangler whoami
```

В браузере войдите в свой аккаунт Cloudflare и подтвердите доступ Wrangler. Не передавайте
OAuth-ссылку, пароли, токены и ключи другим людям. `whoami` должен показать нужный аккаунт.

После проверки аккаунта создайте отдельные ресурсы (один раз):

```powershell
npx wrangler d1 create fckfamousgroup-production
npx wrangler r2 bucket create fckfamousgroup-media
Copy-Item wrangler.production.example.json wrangler.production.json
```

Если R2 попросит включить услугу или добавить платёжные данные, сначала ознакомьтесь
с условиями в своём аккаунте. Введите в `wrangler.production.json` свой `account_id`
и полученный `database_id`. Этот файл игнорируется Git. Он содержит идентификаторы ресурсов,
а не пароли; секреты в него добавлять нельзя. Не повторяйте Copy-Item поверх настроенного файла.

Для **новой пустой** базы примените схему:

```powershell
npx wrangler d1 migrations apply DB --remote --config wrangler.production.json
```

До публикации согласуйте перенос каталога и администратора, как описано выше. Серверные
секреты задаются через Cloudflare Dashboard или интерактивную команду, например:

```powershell
npx wrangler secret put ADMIN_SECRET --config wrangler.production.json
```

Аналогично задаются ADMIN_LOGIN, ADMIN_INITIAL_CREDENTIAL для новой базы и
ADMIN_REQUIRE_MFA со значением true. Для переноса текущего администратора нужен прежний
ADMIN_SECRET; не генерируйте замену без намеренного сброса пароля и MFA.

Затем сборка и публикация:

```powershell
npm run build:cloudflare
npx wrangler deploy --config dist/server/wrangler.json
```

Сборка останавливается, если production-конфигурации нет или в ней остаются заглушки.
Она выполняет существующие проверки секретов и очистку dist от локальных .dev.vars.
Публикуйте только после успешной сборки: не используйте старый dist после ошибки.
Обычная команда `npm run build` сохраняет прежний режим разработки/тестовой публикации.
Деплой не переносит локальную D1/R2 и не меняет DNS в GoDaddy.

## 4. Настроить единственного администратора

Для новой базы из папки store запустите `node scripts/prepare-admin.mjs` в обычном терминале.
Пароль вводится скрыто, значения сохраняются в игнорируемом `.sites-runtime/admin-initial.env`.
Перенесите значения через защищённый интерфейс секретов хостинга; файл не отправляйте в GitHub.
Если переносится существующая база администратора, сохраняйте её ADMIN_SECRET и пароль;
создание нового секрета сделает старый пароль и TOTP недействительными.

После входа на HTTPS настройте аутентификатор и сохраните резервные коды.
Удалите временный `ADMIN_INITIAL_CREDENTIAL` из секретов после успешной настройки.
Регистрации нового администратора на сайте нет. Для передачи управления передайте
пароль через менеджер паролей и настройте второй фактор на устройстве менеджера.

## 5. Подключить домен GoDaddy

Не меняйте DNS до работающей технической публикации.

Для Workers Custom Domain домен должен находиться в активной зоне Cloudflare:

1. Добавить `fckfamous.group` в Cloudflare. Сверить существующие DNS-записи, особенно MX/TXT,
   если домен используется для почты. Сохранить копию старых настроек.
2. Cloudflare покажет два конкретных nameserver. В GoDaddy открыть домен → DNS → Nameservers
   и указать именно эти значения. Не использовать примеры nameserver из чужих инструкций.
3. Дождаться статуса Active в Cloudflare.
4. В настройках опубликованного Worker открыть Domains & Routes → Add → Custom Domain
   и добавить `fckfamous.group`. Решить, нужен ли также www и перенаправление на основной адрес.
5. Дождаться сертификата HTTPS и проверить домен с телефона без Wi-Fi.

Документация: https://developers.cloudflare.com/workers/configuration/routing/custom-domains/

## 6. Проверить перед объявлением запуска

Открываются каталог и пустые категории; работают обе локализации, фото, музыка и ссылки
менеджера. Цены и наличие реальны. Админка требует логин, пароль и второй фактор;
создать администратора через сайт невозможно. Изменение товара сохраняется после
повторной публикации. Есть отдельная резервная копия D1/R2 и секретов у владельца.

Публичность витрины на хостинге и доступ к админке — разные настройки. Секретный URL
админки не заменяет проверку пароля. До выполнения этих шагов домен не считается запущенным.

## Если GitHub пишет Invalid username or token

Не отправляйте пароль или токен в чат. В PyCharm откройте Settings → Version Control →
GitHub, удалите недействующую авторизацию и добавьте аккаунт через Log In via GitHub.
Войдите в браузере в аккаунт владельца репозитория. В окне Git → Push выберите ветку
`develop` и назначение `origin/develop`. Если используете терминал с Git Credential Manager,
повторите `git push -u origin develop` и завершите вход в появившемся браузере.
Если ошибка сохраняется без приглашения войти, удалите только устаревшую запись GitHub
из Windows Credential Manager, затем повторите push. Не удаляйте остальные учётные данные.

После успешной отправки проверьте, что GitHub показывает папку store, а не пустую ссылку
на вложенный репозиторий, и что там нет файлов .dev.vars и папки .sites-runtime.
